Projector · 功能扩展决策报告

📅 2026-05-22 📌 v0.1.0 · 规划中 ⏱ 预估 12–14 人日 📁 4 个 Phase

为个人项目统计工具 Projector 规划深度洞察与工作流集成能力，分阶段增量交付

📋 需求解读

原始需求：「看看还有啥功能值得添加」—— 对已上线的 Rust CLI 工具 Projector (v0.0.1) 进行功能评估与扩展规划。工具当前具备项目发现、扫描分析、快照存储、健康报告等基础能力，需要在现有架构上扩展更有价值的特性。

✅ 已具备

  • list — 项目发现与类型检测
  • scan — 快照录制
  • report — 健康仪表盘 + diff
  • config — TOML 配置管理
  • JSON / Markdown 导出

🔲 新功能

  • inspect — 单项目深度分析
  • stats — 全局聚合统计
  • trend — 跨快照趋势
  • report --sort/--filter
  • Shell 补全 + HTML 导出
  • 快照清理 + 健康告警

用户故事

  • 作为开发者，我想深入查看单个项目的 commit 频率、作者活跃度、文件分布，而不只是看一个健康分
  • 作为团队 Lead，我想一眼看到所有项目的全局统计——平均健康分、类型分布、最危险的项目排行
  • 作为长期用户，我想看项目健康分随时间的变化趋势，知道哪些项目在变好、哪些在恶化
  • 作为日常使用者，我想要 shell 补全提升操作效率，以及一份可分享的 HTML 仪表盘

🧠 方案对比

三个技术维度的方案对比与选型建议：

方案做法性能复杂度维护性
A · 深度 git2 复用现有 git2 库遍历 commit 统计 中等 低 低
B · 外部命令 调用 git log / shortlog 低 低 中
C · 第三方分析库 引入 git-analyze 等 高 高 高

✅ 推荐 A：现有 git2 API 已覆盖 commit 遍历、branch 对比等需求，零额外依赖、零跨平台问题

方案做法性能复杂度维护性
A · clap_complete 官方扩展库，声明式生成 零开销 极低 低
B · 手写脚本 为各 shell 手写补全 零开销 高 高
C · 内联 HTML 模板 Rust 常量字符串嵌入 快 中 低
D · 模板引擎 (tera) 引入重型模板库 中 高 中

✅ 推荐 A+C：clap_complete 官方方案零手写；HTML 仪表盘用内联模板，零额外依赖

方案做法性能复杂度维护性
A · ASCII 折线图 终端字符绘制趋势 快 中 低
B · 位图渲染 生成 PNG/SVG 图 中 高 高

✅ 推荐 A：终端工具回归终端，ASCII 图是 CLI 生态标准做法，零依赖、跨平台

  • 外部 git 命令 (B)： 进程调用开销大，输出解析脆弱，Windows git 输出格式不同导致跨平台问题
  • 第三方分析库 (C)： 引入不稳定依赖，功能冗余，本项目只需极少的 git 统计维度
  • 手写补全 (B)： 每次新增命令需同步更新三份脚本，维护成本远超 clap_complete
  • 模板引擎 (D)： 为单个 HTML 引入重型依赖不值得，内联常量字符串足够
  • 位图渲染 (B)： 超出 CLI 工具职责边界，HTML 导出已涵盖可视化需求

✅ 最终决策

深度 Git2 分析 + 内联模板 + 分 Phase 增量发布

  1. 复用现有技术栈 — 全部基于已有 git2/serde/clap 生态，新增仅 clap_complete 一个依赖
  2. 终端优先 — 深度分析和趋势图在终端内完成，HTML 导出作为补充能力而非核心
  3. 低维护承诺 — 所有新功能以独立 subcmd 模块添加，不修改现有命令的行为
  4. 增量交付 — 4 个 Phase 独立可发布，每阶段产出可用的子命令，互不阻塞
  5. 开发效率 — 无外部重型依赖，Rust 编译链路短，测试覆盖重点在 git 分析和统计正确性

📁 影响文件：subcmd/trend.rs, report.rs, snapshot.rs
Phase 3 · 3 天

🔌 工作流集成

引入 clap_complete 自动生成 bash/zsh/fish 补全。实现 projector export html 生成自包含、响应式、支持暗色模式的仪表盘。新增约 400 行代码、120 行测试。

📁 影响文件：subcmd/completion.rs, subcmd/export.rs, Cargo.toml
Phase 4 · 2 天

⚙️ 运维提效

快照清理命令 projector snapshot prune（保留策略 / dry-run）。scan 完成后自动健康分告警。新增 snapshot 和 alert 配置段。新增约 300 行代码、150 行测试。

📁 影响文件：subcmd/snapshot.rs, scan.rs, config.rs

📎 风险 & 附录

技术风险

风险概率影响缓解措施
大仓库 git 分析慢 中 中 commit 遍历窗口默认限制 365 天，加 --depth 参数控制
HTML 模板维护 中 低 Rust 常量字符串，修改即编译，无运行时模板错误
快照时间戳不均匀 低 低 X 轴按实际时间分布，不均匀不影响数据质量
clap_complete 兼容 低 中 锁定主版本与 clap 一致，回归测试补全生成

不确定性

  • 终端宽度适配： ASCII 趋势图在小终端 (<80 列) 的可读性需实测验证
  • 大仓库性能： monorepo 或超长历史仓库可能在 commit 遍历时触发性能问题
  • HTML 视觉质量： 内联模板的美观度取决于设计投入，可能需要迭代
